01 · THE SCREEN

What each reporting control does

Open Business reports from the app sidebar to see these controls.

A

Database status

Shows whether reports are using the built-in sample database or a SQLite database you configured. “Read only” means report queries cannot change its data.

B

Available tables and columns

Expand this panel to see the tables, columns, and foreign-key join paths supplied to the model. Use these exact names when asking for a specific field.

C

Question box and suggestions

Type a business question in plain language, or select a sample suggestion to fill the box. Questions can be up to 2,000 characters.

D

Model selector

Choose an installed Ollama model for this report. Smaller models can respond faster; larger models may be more capable but use more memory.

E

Run report

Select the up-arrow button to send the question and schema to Ollama. It is enabled when you have entered a question and selected a model.

F

Summary and results table

Read the model’s short description, then inspect the returned columns and rows. Results are capped at 100 rows; a “limited to 100” note means more rows matched.

G

View generated SQL

Expand this section to inspect the exact SQL that ran. Check its filters, joins, grouping, and totals before relying on a report.

H

Retry question

If a generated query has a SQLite syntax or schema error, the app asks the model once to correct it. If that still fails, use this button to resubmit the original question with the same model.

Each report is independent. The reporting feature does not send earlier questions or results as chat history. Instead of typing “try again” or “show me that order,” use Retry question or include the relevant customer, order ID, date, or other details in a new question.

02 · BEHIND THE SCENES

How a report is produced

The model writes a query; SQLite, not the model, reads the database and calculates the returned rows.

  1. 1

    The app reads the schema

    It finds the available table and column names in the configured SQLite database.

  2. 2

    The question goes to Ollama

    The app sends your question, the schema, and (for the demo database) sample-sales definitions to the selected model.

  3. 3

    The model returns a report query

    Ollama returns a short summary and one SQLite SELECT query. If a SQLite syntax/schema error occurs, the app requests one corrected query.

  4. 4

    The app checks and runs the query

    The query must pass the read-only checks, then it runs against a read-only database connection. The app returns the summary, SQL, and up to 100 rows.

Successful report workflow

  1. QuestionBrowser checks the text and selected model.
  2. →
  3. API requestrunBusinessReport() posts to the report endpoint.
  4. →
  5. Generate and validateService asks Ollama for SQL, then applies the read-only checks.
  6. →
  7. Execute and displaySQLite returns rows; the browser renders the summary, table, and SQL.

SQL error and repair workflow

  1. SQLite errorA syntax or schema error occurs while executing the checked SQL.
  2. →
  3. One correctionThe error and failed SQL go back to Ollama once.
  4. →
  5. Check againThe replacement SQL must pass the same safety checks.
  6. →
  7. Result or errorSuccess displays rows; another failure is shown with Retry question.
03 · CODE MAP

Classes and functions in the request path

These are the reporting-specific parts of the app, in the order they participate. This feature uses SQLite directly through Microsoft.Data.Sqlite; it does not use Entity Framework or a DbContext.

Browser UI · wwwroot/app.js

  • setWorkspaceMode() switches to reports and loads database choices with GET /api/reports/databases. loadReportSchema() requests the selected database's schema and displays its tables and join paths.
  • The database selector reloads the schema and dataset-specific suggestions. runBusinessReport() checks the question, selected database and model, and busy state, then posts all three values to the report API. Retry keeps the original database and model.
  • renderReportResult() builds the summary, row count, results table, and expandable SQL view.
  • api() sends HTTP requests and extracts readable problem titles/details from error responses.

Startup and dependency setup · Program.cs

Validates that OLLAMA_BASE_URL is an absolute HTTP/HTTPS URL. When BUSINESS_DB_PATH is absent, it registers the built-in Sales and Access Control demos in BusinessDatabaseCatalog; when set, only that existing SQLite file is registered. It initializes the catalog, registers the report service, and maps the endpoints.

HTTP boundary · BusinessReportEndpoints

MapBusinessReports() defines GET /api/reports/databases, GET /api/reports/schema?databaseId=…, and POST /api/reports/query. The handlers resolve a requested database and convert invalid IDs and report failures into HTTP problem responses.

Service contract · IBusinessReportService

Declares schema lookup by optional database ID and report execution from a request. This lets the endpoint use the reporting service without depending on its implementation.

Database registry · BusinessDatabaseCatalog

Lists registered database IDs and display names, chooses the default when an older API caller omits an ID, rejects unknown IDs, and initializes every registered database. Selection is passed per request rather than stored as mutable global state.

Report orchestration · BusinessReportService

  • GetSchemaAsync() resolves the selected database and reads table names, columns, and foreign-key relationships so the model has join paths.
  • AskAsync() resolves the database from the request, obtains its schema, checks that tables exist, asks for SQL, validates it, executes against that database, and assembles a response identifying the dataset. A SQLite syntax/schema error gets one repair attempt.
  • GenerateSqlAsync() sends the question, schema, and applicable business rules to Ollama and parses its JSON summary and SQL.
  • ValidateReadOnlySql() enforces the query rules before execution; SkipQuoted() handles quoted SQL text while scanning it.
  • ExecuteReportAsync() runs the query and collects its columns and rows; NormalizeSqlValue() converts binary values to Base64 and database nulls to JSON nulls.

SQLite lifecycle · BusinessDatabase

  • InitializeAsync() verifies that a configured custom file exists; for built-in demos it creates/seeds the sales schema or runs the access-control SQL setup script.
  • OpenReadOnlyConnectionAsync() opens a read-only connection and enables SQLite query-only mode.
  • Id, DisplayName, and BusinessRules identify the database and give the model dataset-specific context; IsDemoData marks sample data.

Request and response types · BusinessReportModels

BusinessReportRequest carries the optional database ID, model, and question. BusinessSchemaResponse and BusinessTableSchemaResponse describe the selected database schema. BusinessReportResponse carries the summary, SQL, rows, truncation flag, database identity, and timestamp. ReportDatabaseSelectionException represents an unavailable ID; ReportQueryException represents SQL rejected by the safety check.

04 · VALIDATION AND ERROR FLOW

What is checked before a result is returned

Validation happens at several boundaries. A model-generated query is never executed just because Ollama returned it.

  1. 1

    Browser form checks

    The question is trimmed and must not be empty; a database and model must be selected; another report cannot run while one is already in progress. The textarea also limits input to 2,000 characters.

  2. 2

    API request checks

    BusinessReportRequest requires a model and question, limits the model name to 200 characters and the question to 2,000, and ASP.NET validation rejects invalid requests.

  3. 3

    Database and schema checks

    The catalog rejects unknown database IDs with HTTP 400. At startup, a configured custom database must exist. During a report, the service enumerates non-internal tables, columns, and foreign-key relationships; an empty schema cannot produce a report.

  4. 4

    Ollama response checks

    Non-success HTTP responses are surfaced. The response must contain JSON with non-empty string summary and sql properties; empty, malformed, or incomplete output is rejected.

  5. 5

    SQL safety checks

    Generated SQL is limited to 10,000 characters, cannot contain comments or multiple statements, and must start with SELECT or WITH containing a SELECT. Known write/unsafe tokens and SQLite/PRAGMA internal names are rejected. Quoted strings are skipped safely, and unterminated quotes are rejected. The model is instructed to use the discovered schema; SQLite checks actual syntax and table/column names during execution.

  6. 6

    Read-only execution limits

    Execution uses a read-only, query-only connection with a 10-second command timeout. At most 100 rows are returned; if another row exists, the response marks the results as truncated.

  7. 7

    One bounded SQL correction

    A SQLite syntax/schema error (SQLite error code 1) is sent back to Ollama with the failed SQL for one correction attempt. The corrected SQL goes through the same safety checks. There is no unlimited retry loop.

How failures reach the UI

Rejected SQL becomes HTTP 400; a query SQLite cannot run becomes 422; Ollama/network or invalid-model output becomes 502; an Ollama timeout becomes 504. The browser displays the problem title/detail and offers a retry for the original question.

Where errors are not hidden

If the single repair still fails, the SQLite error is returned instead of a success-shaped empty report. If the SQL is unsafe, it is rejected before SQLite executes it.

05 · GETTING USEFUL RESULTS

How to ask clearer questions

Be specific about the metric, grouping, filters, and time period you want.

Less specific

“Show sales.”

More specific

“What was total completed sales by region in 2026? Show the highest-revenue region first.”

  • Name the measure: order count, units sold, or revenue.
  • Name the grouping: by region, customer, product, or month.
  • Include filters such as completed orders, a customer name, or a date range.
  • For “top” or “most popular” requests, specify whether you mean revenue, quantity, or number of orders.
  • For details, identify the order or customer explicitly. The model cannot infer which earlier result you mean.

In the sample sales database, revenue is quantity multiplied by unit price, and completed orders count as sales by default. These definitions are not assumed for a custom database.

06 · DATA AND SAFEGUARDS

What is sent, and what is protected

Sent to the configured Ollama server

The report question and database schema (table and column names) are sent to the server configured by OLLAMA_BASE_URL. By default, Ollama runs locally at http://localhost:11434.

Queried locally by the app

The generated SQL runs against SQLite from the app. Query results are not sent back to the model as part of report generation.

Read-only query limits

The app accepts a single read-only SELECT (or a WITH query ending in SELECT), uses a query-only SQLite connection, and caps returned rows at 100.

Review before decisions

Generated SQL and summaries can still be logically wrong even when they run. Inspect the SQL and confirm important results independently.

Without BUSINESS_DB_PATH, select either built-in sample database from the report composer. Setting BUSINESS_DB_PATH replaces those choices with the configured, existing SQLite file.

07 · TROUBLESHOOTING

If something goes wrong

No model is available
Install or pull a model in Ollama, then refresh the app’s model list and select it in the report composer.
Ollama is disconnected
Start Ollama and check its configured URL. The app defaults to http://localhost:11434.
The query still fails
The app makes one automatic correction attempt for SQLite syntax/schema errors. If it cannot repair the query, read the error, make the question more specific, or use Retry question.
The result looks incomplete or unexpected
Open View generated SQL and verify its joins, filters, grouping, and row limit. Try defining what “popular,” “sales,” or “profit” means for your report.

Business reports are a local reporting assistant, not a replacement for checking important figures.
