01 · THE SCREEN

What each reporting control does

Open Database Chat to ask questions. Manage connections separately from Database connections in the sidebar.

A

Database status

Shows which built-in demo or saved SQLite/SQL Server profile is selected. Report queries are validated as reads; use a read-only SQL Server account as an additional permission boundary.

B

Available tables and columns

Expand this panel to see the tables, columns, and foreign-key join paths supplied to the model. Use these exact names when asking for a specific field.

C

Question box and suggestions

Type a business question in plain language, or select a sample suggestion to fill the box. Questions can be up to 2,000 characters.

D

Model selector

Choose an installed Ollama model for this report. Smaller models can respond faster; larger models may be more capable but use more memory.

E

Run report

Select the up-arrow button to send the question and schema to Ollama. It is enabled when you have entered a question and selected a model.

F

Summary and results table

Read the model’s short description, then inspect the returned columns and rows. Results are capped at 100 rows; a “limited to 100” note means more rows matched.

G

View generated SQL

Expand this section to inspect the exact SQL that ran. Check its filters, joins, grouping, and totals before relying on a report.

H

Retry question

If a generated query has a recognized database syntax or schema error, the app asks the model once to correct it. If that still fails, use this button to resubmit the original question with the same model.

I

Database connections menu

Open this separate workspace from the sidebar to add, review, or remove database profiles. Return to Database Chat to select a connection and ask questions.

J

Chat Safety Settings

Select a saved database profile and local model, then choose Generate basic settings to draft context, hints, validation notes, checklist items, and test prompts from its schema. The generated draft replaces the editor fields; review it and save when ready. Built-in and environment-configured databases are not editable here.

Each report is independent. The reporting feature does not send earlier questions or results as chat history. Instead of typing “try again” or “show me that order,” use Retry question or include the relevant customer, order ID, date, or other details in a new question.

02 · BEHIND THE SCENES

How a report is produced

The model writes a query; the selected database, not the model, reads the data and calculates the returned rows.

  1. 1

    The app reads the schema

    It finds the available table and column names in the selected SQLite or SQL Server database.

  2. 2

    The question goes to Ollama

    The app sends your question, the schema, and (for the demo database) sample-sales definitions to the selected model.

  3. 3

    The model returns a report query

    Ollama returns a short summary and a provider-specific SELECT query. If a recognized database syntax/schema error occurs, the app requests one corrected query.

  4. 4

    The app checks and runs the query

    The query must pass the read-only checks, then it runs against a read-only database connection. The app returns the summary, SQL, and up to 100 rows.

Successful report workflow

  1. QuestionBrowser checks the text and selected model.
  2. →
  3. API requestrunBusinessReport() posts to the report endpoint.
  4. →
  5. Generate and validateService asks Ollama for SQL, then applies the read-only checks.
  6. →
  7. Execute and displayThe selected database returns rows; the browser renders the summary, table, and SQL.

SQL error and repair workflow

  1. Database errorA recognized syntax or schema error occurs while executing the checked SQL.
  2. →
  3. One correctionThe error and failed SQL go back to Ollama once.
  4. →
  5. Check againThe replacement SQL must pass the same safety checks.
  6. →
  7. Result or errorSuccess displays rows; another failure is shown with Retry question.

Connect or remove a database profile

  1. Enter profileChoose SQLite or SQL Server, then enter a name and connection string.
  2. →
  3. Check accessThe app opens the connection and runs SELECT 1.
  4. →
  5. Encrypt and registerSuccessful profile details are encrypted locally and added to the selector.
  6. →
  7. Remove safelyRemoving unregisters the profile; it does not delete the database.

Customize a saved profile

  1. Open guidanceChoose a saved profile in Database connections.
  2. →
  3. Add contextWrite definitions, join hints, or validation notes for reports.
  4. →
  5. Generate settingsUse the selected local model to draft the text fields, checklist, and test prompts from the schema.
  6. →
  7. Review and saveCheck the generated draft, then save context, checklist, and up to three prompts with the profile.
03 · CODE MAP

Classes and functions in the request path

These are the reporting-specific parts of the app, in the order they participate. SQLite and SQL Server are accessed through ADO.NET providers; this feature does not use Entity Framework or a DbContext.

Browser UI · wwwroot/app.js

  • setWorkspaceMode() switches between General Chat, Database Chat, Database connections, and Chat Safety Settings. The database and safety-settings workspaces load profile choices with GET /api/reports/databases; loadReportSchema() requests the selected report database's schema.
  • The database selector reloads the schema and dataset-specific suggestions. runBusinessReport() checks the question, selected database and model, and busy state, then posts all three values to the report API. Retry keeps the original database and model.
  • renderReportResult() builds the summary, row count, results table, and expandable SQL view.
  • api() sends HTTP requests and extracts readable problem titles/details from error responses.

Startup and dependency setup · Program.cs

Validates that OLLAMA_BASE_URL is an absolute HTTP/HTTPS URL. It registers both built-in demos, adds an existing BUSINESS_DB_PATH as the default when configured, loads saved profiles, and initializes demo data. ASP.NET Core Data Protection encrypts saved connection strings in local app storage.

HTTP boundary · BusinessReportEndpoints

MapBusinessReports() defines database-list, schema, and report-query endpoints, plus local-only profile add/remove, guidance GET/PUT, safety-settings draft, and test-prompt generation routes. The removal endpoint unregisters the profile but never deletes its database.

Service contract · IBusinessReportService

Declares schema lookup by optional database ID, report execution from a request, and schema-based test-prompt generation. This lets the endpoint use the reporting service without depending on its implementation.

Database registry · BusinessDatabaseCatalog

Lists registered database IDs, provider names, and removal eligibility; chooses a default when an older API caller omits an ID; rejects unknown IDs; and initializes demo data. Profiles can be registered or removed while the app runs. Selection is passed per request rather than stored as mutable global state.

Report orchestration · BusinessReportService

  • GetSchemaAsync() resolves the selected provider and reads table names, columns, and foreign-key relationships so the model has join paths.
  • GenerateTestPromptsAsync() asks the selected model for three questions using the profile schema and guidance, without querying database rows.
  • GenerateDatabaseSafetySettingsAsync() drafts all profile text fields, checklist items, and test prompts from schema only; the user reviews and saves the returned draft.
  • AskAsync() selects provider-specific SQL instructions, validates the query, executes it through the database adapter, and assembles a response identifying the data source. Recognized syntax/schema errors get one repair attempt.
  • GenerateSqlAsync() sends the question, schema, provider, and applicable business rules to Ollama and parses its JSON summary and SQL.
  • ValidateReadOnlySql() enforces shared and provider-specific query rules before execution; SkipQuoted() handles quoted SQL text while scanning it.
  • ExecuteReportAsync() runs the query and collects its columns and rows; NormalizeSqlValue() converts binary values to Base64 and database nulls to JSON nulls.

Database adapters · IReportDatabase

  • BusinessDatabase opens SQLite files in read-only mode and enables SQLite query-only mode. It also initializes the built-in demo fixtures.
  • SqlServerBusinessDatabase opens SQL Server connections with ApplicationIntent=ReadOnly and pooling disabled; this is a routing hint, not a permission boundary.
  • The shared contract exposes provider, schema, connection, and repairable-error behavior without leaking provider details into the API.

Saved profile lifecycle · DatabaseProfileService

  • The Database connections workspace lets users add and remove profiles outside the report/chat composer. Chat Safety Settings is a separate workspace for editing a saved profile's guidance and prompts. AddAsync() checks a connection with SELECT 1 before saving and registering it.
  • Saved profiles can store context, reporting hints, informational validation notes, checklist items, and up to three test prompts. Saving settings rebuilds the registered adapter so new rules apply immediately.
  • EncryptedDatabaseProfileStore serializes profiles and protects them with ASP.NET Core Data Protection. The connection string is never included in the database-list response.
  • SQLite profiles must reference an existing file. Removing a profile unregisters it and removes its saved connection string; the database file/server database is not modified.

Request and response types · BusinessReportModels

BusinessReportRequest carries the optional database ID, model, and question. Each question is independent; include names or IDs explicitly. BusinessReportResponse carries the summary, SQL, rows, truncation flag, database identity, clarification flag, and timestamp. Clarification responses never execute the model's SQL or return rows. ReportDatabaseSelectionException represents an unavailable ID; ReportQueryException represents SQL rejected by the safety check.

04 · VALIDATION AND ERROR FLOW

What is checked before a result is returned

Validation happens at several boundaries. A model-generated query is never executed just because Ollama returned it.

  1. 1

    Browser form checks

    The question is trimmed and must not be empty; a database and model must be selected; another report cannot run while one is already in progress. The textarea also limits input to 2,000 characters.

  2. 2

    API request checks

    BusinessReportRequest requires a model and question, limits the model name to 200 characters and the question to 2,000, and ASP.NET validation rejects invalid requests.

  3. 3

    Database and schema checks

    The catalog rejects unknown database IDs with HTTP 400. A saved SQLite profile must point to an existing file; a profile is checked with SELECT 1 before registration. During a report, the service enumerates tables, columns, and foreign-key relationships; an empty schema cannot produce a report.

  4. 4

    Ollama response checks

    Non-success HTTP responses are surfaced. The response must contain JSON with non-empty string summary and sql properties; empty, malformed, or incomplete output is rejected.

  5. 5

    SQL safety checks

    Generated SQL is limited to 10,000 characters, cannot contain comments or multiple statements, and must start with SELECT or WITH containing a SELECT. Known write/unsafe tokens and internal schema names are rejected; provider-specific syntax such as LIMIT versus TOP is checked. Quoted strings are skipped safely, and unterminated quotes are rejected. The selected database validates actual syntax and table/column names during execution.

  6. 6

    Read-only execution limits

    SQLite uses a read-only, query-only connection. SQL Server uses read-only application intent, but that is not an authorization control: grant the SQL Server login only the required SELECT permissions. Queries have a 10-second command timeout and return at most 100 rows.

  7. 7

    One bounded SQL correction

    Recognized provider-specific syntax or schema errors are sent back to Ollama with the failed SQL for one correction attempt. The corrected SQL goes through the same safety checks. There is no unlimited retry loop.

Chat Safety Settings checks

Saved guidance fields are limited to 2,000 characters, checklist items to 25 entries of 200 characters each, and test prompts to three unique entries of 200 characters each. Validation guidance is advisory text for the model, not an application-enforced database constraint.

How failures reach the UI

Rejected SQL becomes HTTP 400; a query the selected database cannot run becomes 422; Ollama/network or invalid-model output becomes 502; an Ollama timeout becomes 504. The browser displays the problem title/detail and offers a retry for the original question.

Where errors are not hidden

If the single repair still fails, the database error is returned instead of a success-shaped empty report. If the SQL is unsafe, it is rejected before execution.

05 · GETTING USEFUL RESULTS

How to ask clearer questions

Be specific about the metric, grouping, filters, and time period you want.

Less specific

“Show sales.”

More specific

“What was total completed sales by region in 2026? Show the highest-revenue region first.”

  • Name the measure: order count, units sold, or revenue.
  • Name the grouping: by region, customer, product, or month.
  • Include filters such as completed orders, a customer name, or a date range.
  • For “top” or “most popular” requests, specify whether you mean revenue, quantity, or number of orders.
  • For details, identify the order or customer explicitly. The model cannot infer which earlier result you mean.

In the sample sales database, revenue is quantity multiplied by unit price, and completed orders count as sales by default. These definitions are not assumed for a custom database.

06 · DATA AND SAFEGUARDS

What is sent, and what is protected

Sent to the configured Ollama server

The report question, database schema (table and column names), and saved-profile context, reporting hints, and validation notes are sent to the server configured by OLLAMA_BASE_URL. Generating test prompts sends the schema and that guidance, not database rows. By default, Ollama runs locally at http://localhost:11434.

Queried locally by the app

The generated SQL runs against the selected database from the app. Query results are not sent back to the model as part of report generation.

Read-only query limits

The app accepts a single read-only SELECT (or a WITH query ending in SELECT) and caps returned rows at 100. SQLite is opened query-only; SQL Server still requires a least-privilege read-only login.

Review before decisions

Generated SQL and summaries can still be logically wrong even when they run. Inspect the SQL and confirm important results independently.

Checklist and saved prompts

Checklist items are stored with an encrypted saved profile but are not sent to Ollama. Generated test prompts are editable and are also saved with that profile; selecting it in Database Chat displays them as clickable suggestions.

Both built-in demos stay available. Set BUSINESS_DB_PATH to add an existing SQLite file as the default, or use Database connections in the sidebar to add SQLite or SQL Server connections. Removing a profile does not delete the database. Saved connection strings are encrypted in local app storage.

07 · TROUBLESHOOTING

If something goes wrong

No model is available
Install or pull a model in Ollama, then refresh the app’s model list and select it in the report composer.
Ollama is disconnected
Start Ollama and check its configured URL. The app defaults to http://localhost:11434.
A database profile cannot connect
For SQLite, check that the file exists and the app user can read it. For SQL Server, check network access and use a dedicated account with the required SELECT permissions. A saved but unavailable profile does not prevent app startup; restore its access or remove it. Connection strings are not returned by the profile list.
The query still fails
The app makes one automatic correction attempt for recognized database syntax/schema errors. If it cannot repair the query, read the error, make the question more specific, or use Retry question.
The result looks incomplete or unexpected
Open View generated SQL and verify its joins, filters, grouping, and row limit. Try defining what “popular,” “sales,” or “profit” means for your report.

Database Chat is a local reporting assistant, not a replacement for checking important figures.
